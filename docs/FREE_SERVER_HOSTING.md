# Free server hosting and password accounts

The complete app can run as one Render Free Docker web service, independently of the owner's computer. Render supplies a stable `https://<service>.onrender.com` address and TLS. The temporary `trycloudflare.com` hostname belongs to the old local tunnel and cannot be moved to Render. No domain purchase is required for the Render address.

## Deployment

1. Use a Render Free/Hobby workspace without a payment method. Free services sleep after 15 idle minutes and can take about a minute to wake up. The workspace has 750 free instance hours/month; bandwidth/build quotas also apply. Without a payment method, exhausted quotas suspend services/builds rather than create a paid overage.
2. Keep the application source in a private GitHub deployment repository. The previous public documentation repository can remain separate. `scripts/prepare-hosted-source.mjs` prepares an explicit source allowlist and scans it against configured credentials; it excludes `.env.local`, screenshots, browser caches and the entire `work` directory. Its output is ignored locally, never application content.
3. Connect Render only to that repository, then create a **Web Service**, runtime **Docker**, instance **Free**, region **Oregon**. The root `Dockerfile` installs Node and a Python virtual environment. Use `/sign-in` as the health check path and leave automatic deploys off for this initial test.
4. Enter `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, and `GEMINI_API_KEY` in Render's environment settings. Keep secrets out of Git, screenshots and chat. Use the publishable/anon Supabase key, never service-role. Set `INTAKE_PROVIDER=gemini`, `GEMINI_MODEL=gemini-3.5-flash-lite`, and `TRANSITOUS_ENABLED=true`; keep the Google project on its free tier. The included `render.yaml` documents these values.
5. The runtime takes its exact trusted HTTPS origin from `RENDER_EXTERNAL_URL`; a custom domain needs `PUBLIC_APP_ORIGIN` set to that exact origin. It forces authenticated access and free search adapters. Duffel live requests, RapidAPI, Booking Demand and Tictactrip remain disabled.
6. In Supabase, keep email confirmation enabled. The **Confirm sign up**, **Magic link or OTP**, and **Reset password** email bodies must contain the numeric `{{ .Token }}`. Existing custom Brevo SMTP continues to deliver these messages. The code-only flow does not need an authentication redirect URL; configure the hosted site URL and exact allowed redirects if enabling link-based emails later.
7. Verify signup → email confirmation → dashboard, sign out → password sign-in without another email, recovery → email code → new password, and account sync. Run a small flight search on the hosted server before inviting testers; Google's behavior from a datacenter can differ from home access.

## Account behavior

`/sign-in` has functional sign-in/create-account modes. New accounts choose a password, then confirm their email once. Subsequent password logins use `signInWithPassword`; no email-send request is made. Unconfirmed accounts cannot enter the dashboard. Passwords go directly through the server to Supabase Auth, with no application logging or storage; session tokens stay in HttpOnly cookies.

Existing email-code accounts can sign in once with **Use an email code**, which opens **Account → Create or change your password** after verification. The signup screen also links directly to this existing-account path. Signup and sign-in codes use Supabase's current `email` verification type; old clients sending `signup` are normalized on the server. Forgot-password recovery keeps its separate OTP type. Requesting another code clears the old entry, and the form directs users to the newest email. Passwords must have 10–128 characters; confirmation is checked in the form. Auth writes check the exact website origin, validate inputs, throttle attempts and return no session tokens in JSON.

## Free-tier limits and validation

The free container allows one active Python flight worker (two leg requests within that worker); simultaneous extra searches receive a busy message. Its Node heap is limited to 256 MB. The Python cache and local usage counters are ephemeral and reset when the service restarts; private trips persist in the existing Supabase database. These local counters are not durable billing enforcement. The service never enables a paid travel adapter.

This setup is for a small test group, not an uptime or unlimited-use promise. Supabase Free and Brevo's free email limits still apply. Do not enable billing or add a payment method as part of deployment. No bookings or payments are implemented.

The password changes passed the 445-test regression suite (one benchmark test skipped), TypeScript, targeted ESLint, and a production Webpack build. Render then completed the Linux Docker build and deployed the service. Its first build exposed an omitted `pnpm-workspace.yaml`; including that file preserved the frozen lockfile's overrides and resolved the failure.
